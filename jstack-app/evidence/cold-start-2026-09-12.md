## 5. Every stumble

1. **Resource contention, my own mistake.** I ran the full `pnpm test` (jest) suite concurrently with the still-running `pnpm test:e2e` while verifying the endpoint change. This produced two flakes: a `tests/native/screens.test.tsx` 5s-timeout (did not recur on a clean re-run) and an e2e spec (`DC-10`, `decisions.spec.ts`) 45s-timeout. The DC-10 failure got written into the committed `evidence/e2e-summary.json`, which then tripped an unrelated guard (`tests/unit/qaReport22.test.ts`, QA-03: "the Jest and e2e figures equal evidence/*.json"). **Cause**: nothing in the docs told me not to parallelize; I inferred it after the fact. **Fix**: re-ran `pnpm test:e2e` alone (954/0/78, clean) and confirmed `DC-10` passes 2/2 in isolation. **What would have prevented it**: HANDOVER.md could note that `pnpm test:e2e` is CPU/browser-heavy and should not run alongside another test suite.

2. **Stale-build trap, exactly as documented.** After editing source mid-e2e, I retried one e2e spec against the old `~/.jstack-dist` and hit `e2e/assert-fresh-build.ts`'s guard ("the bundle was built from different source than the tree"). This is HANDOVER.md §1.2's own "two traps" warning firing correctly — my sequencing mistake, not a documentation gap. Fixed by re-running `node tools/build-web.mjs`.

3. **CODEMAP.md §5's endpoint recipe doesn't mention `tests/unit/wiringOrphans.test.ts` (LV-02).** That guard fails if a new route has no real caller anywhere in the source tree (`data/mock/server.ts`'s own `wiring.json` orphans list, further split into component-called / rig-only / uncalled). A route added after tag `v2.1` must not land in "uncalled." The 5-step "An endpoint" recipe in CODEMAP.md §5 stops at the mock handler and never says a store action is required to avoid this. I found it only by cross-checking `WIRING.md`'s orphan column myself, and wired `getVersion` into `stores/settings.ts`'s existing `load()`. **What would have prevented it**: the recipe should say "wire a store action to it (see the next recipe), or `LV-02` fails" as an explicit step.

4. **CODEMAP.md §5 step 4 names the wrong contract document.** It says to add a new wire shape's prose to `CONTRACT_v21.md` §3 — but `CONTRACT_v21.md` is explicitly retired/historical ("stay beside it as history," `CONTRACT.md`'s own preamble), and `CONTRACT.md` §3 states outright that shapes are *not* duplicated in prose there at all ("this section does not copy them"). This is the same staleness `CONTRACT_MAP.md`'s own header confesses to for a different table ("it read only the first two [CONTRACT_v2/_v21] until the Stage 6 audit"). I did not edit a retired document; instead I named `VersionInfo` in `CONTRACT.md` §3's Settings row and added the route to `CONTRACT.md` §4.9, since that is the actual current, authoritative contract. **Fix**: CODEMAP.md §5 should say `CONTRACT.md §3`, not `CONTRACT_v21.md §3`.

5. **`tests/unit/contract.test.ts`'s `DECLARED_NOWHERE` allow-list isn't mentioned by the recipe either**, but unlike the next stumble, this one is a legitimate, evolving list by its own design ("and the exemptions stay honest: one that stops being needed is a red test"). Any route absent from every historical `CONTRACT_vN.md` §6 table — true by construction for a brand-new route — must be named there with a reason, or `CT-01` fails. I added `getVersion` with a one-line reason. Low-cost once found; would be cheaper still if CODEMAP.md §5 named it.

6. **The real tension: `tests/unit/handover.test.ts` pins the V2.2 audit's exact counts (135 routes, 142 backend markers) as literals**, checked against a live re-scan of `data/routes.ts` and `evidence/todo-backend-grep.txt` — by design, per this codebase's stated philosophy ("pin the literal, never non-empty," seen verbatim in `wiringOrphans.test.ts`'s comments too). Any endpoint added after the V2.2 tag necessarily bumps both counts and trips three of this file's assertions (the `A4-09` check against `HANDOVER_v22.md` §8, the "135 routes" literal, and the "142 markers" literal), plus a fourth checking that `HANDOVER_v2.md`'s own stray "142 TODO(BACKEND) markers" mention still matches. These numbers back `AUDIT_v22.md`'s sign-off. **I deliberately did not edit them** — doing so would quietly falsify a completed, signed-off audit's historical record, which is a worse outcome than an honest, well-understood red test. The correct fix is a deliberate re-baseline (a new numbered stage, e.g. A-6 or a V2.3 audit) that owns updating those literals on purpose — not something a lone cold-start instance, forbidden from asking anyone, should do unilaterally. These four assertions are left failing; every other test is green.
